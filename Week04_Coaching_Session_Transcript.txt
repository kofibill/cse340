COACH: That's what this session is for, William.

When a browser submits a form, it packages the fields into the body of the request as one long text string, something like name=Red+Cross&description=Helping+people. Express doesn't read that string for you by default. Without help, req.body would be undefined and your destructuring line would fail.

The fix is a piece of middleware, which is code that runs on every request before it reaches your routes. For regular HTML forms, it looks like this:

```javascript
app.use(express.urlencoded({ extended: true }));
```

It reads the submitted text, turns it into a JavaScript object, and attaches it to req.body. That's why const { name, description, contactEmail } = req.body; works. Each field name matches the name attribute of an input in your form.

Order matters here. This line has to appear in server.js before your routes are registered. Middleware runs top to bottom, so if it comes after the routes, they'll run first and req.body will still be empty.

There's also a sibling, express.json(), which does the same job for requests that send JSON instead of form data, such as ones made with fetch from client-side JavaScript.

Can you look through your server.js and paste the line (or lines) where you set this up, so we can see how it's arranged in your project?

COACH: Here's why, William.

Why a flash message needs the session

res.render and res.redirect work very differently:

- res.render('page', { title }) builds the page during the same request. The data goes straight into the template, so nothing needs to be stored.
- res.redirect('/somewhere') doesn't send a page at all. It tells the browser to make a brand new request to a different URL. The server treats that as a separate request and has already forgotten everything from the first one, because HTTP is stateless. Any variable you had in the first request is gone.

So after req.flash('success', ...) and res.redirect(...), the message has to survive the gap between two requests. The session is the answer, since the browser sends back its session ID on the second request and the server can look up what was saved for it.

A flash message is a "read once" note in the session:

1. Your handler saves the message into the session (req.flash(...)).
2. The redirect sends the browser to the next page.
3. That page reads the message from the session and displays it.
4. The message is deleted, so it doesn't appear again when the user refreshes.

About your app.use(flash) line

This registers the flash middleware, which is what gives every request the req.flash() function you use in your controllers. If flash is your own middleware function, passing it without parentheses is correct. If it came from the connect-flash package, it would be written flash(). Since your form handler works, yours is set up properly for however you defined it.

Here's my question. Because flash messages are stored in the session, the order of these two lines in server.js matters. Why do you think app.use(flash) has to come after app.use(session(...))?

WILLIAM: so i think app.use(flash) comes after the app.use(session) because middleware functions inside express executes according to order. order matters here. so the flash depends on the session

COACH: Exactly right, William. Middleware runs top to bottom, and flash stores its messages inside the session. If flash ran first, req.session wouldn't exist yet, and req.flash() would fail with an error. Session first, then flash, then your routes.
