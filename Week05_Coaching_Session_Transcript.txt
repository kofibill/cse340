- 10 is the cost factor (also called salt rounds). You pass it to bcrypt.genSalt(10). It means the hashing work is repeated 2^10 (1,024) times, and each +1 doubles the time.

WILLIAM: i cannot think of any answer, please explain to me why

COACH: That's fine, William. This is a tricky idea, so here's the explanation.

The problem without a salt

A hash function always gives the same output for the same input. If Pass1234 always hashes to the same string, two things go wrong:

1. Duplicates are visible. If someone gets a copy of your database, every user with the same hash obviously has the same password. Cracking one cracks them all.
2. Precomputed tables work. Attackers keep huge lists of common passwords and their hashes (called rainbow tables). They just look your hash up in the list, with no cracking needed.

What the salt does

bcrypt.genSalt(10) creates a new random string every time it's called. That string is mixed into the password before hashing, so:

- User A with Pass1234 and salt x7Qp... gets one hash.
- User B with Pass1234 and salt m2Zk... gets a completely different hash.

The duplicates disappear, and a precomputed table is useless because the attacker would need a separate table for every possible salt.

Where the salt is stored

You don't need a separate column for it. bcrypt writes the salt and the cost factor into the hash string itself. A stored value looks like $2b$10$<salt><hash>, and the 10 in there is your cost factor.

Here's my question. Since every hash uses a different random salt, you can't just hash the login password again and compare strings the way you might expect. How do you think the server checks whether a password entered at login is correct?

COACH: Your instinct is right that the server compares what was entered at login with what's stored. The detail is that it can't compare the two strings directly. The stored value is a salted hash, and the password typed at login is plain text, so they'd never be equal. Instead, bcrypt provides a function for this:

```javascript
const match = await bcrypt.compare(plainPasswordFromLogin, storedHash);
```

bcrypt.compare reads the salt and cost factor out of the stored hash and hashes the entered password with those same settings. It returns true if the results match and false if they don't. That's why the salt can live inside the hash string, and why the server never needs to know or store the original password.

```javascript
const requireRole = (role) => {
    return (req, res, next) => {
        // Check if user is logged in first
        if (!req.session || !req.session.user) {
            req.flash('error', 'You must be logged in to access this page.');
            return res.redirect('/login');

        // Check if user's role matches the required role
        if (req.session.user.role_name !== role) {
            req.flash('error', 'You do not have permission to access this page.');
            return res.redirect('/dashboard');
        }

        // User has required role, continue
        next();
    };
};
```

COACH: No problem, William. This is one of those lines that's easy to copy without knowing why it's written that way.

What the guard protects against

In EJS, isLoggedIn is a variable that has to be handed to the template, usually through res.render(...) or res.locals. If it was never provided on some request, writing if (isLoggedIn) crashes the page with a ReferenceError: isLoggedIn is not defined. JavaScript throws that error whenever you read a variable that doesn't exist at all.

typeof is the one exception. Using typeof on a variable that doesn't exist doesn't throw. It just returns the string 'undefined'. So the condition works like this:

- typeof isLoggedIn !== 'undefined' asks "does this variable exist at all?" and never crashes.
- && isLoggedIn then asks "and is it true?" It only runs if the first part passed.

If the variable is missing, the whole condition is false, the else branch runs, and the visitor simply sees Register and Login instead of a crashed page. It's a defensive habit that keeps one forgotten variable from breaking every page that includes your header.

Where the variable usually comes from

Since the header is included on every page, isLoggedIn is normally set once in middleware in server.js, so every template gets it automatically.

COACH: Here's how that middleware works, William.

How it works

1. app.use((req, res, next) => { ... }) runs on every request, before your routes.
2. res.locals is a special object. Anything you attach to it is automatically available in every EJS template for that request, with no need to pass it through res.render.
3. It starts with res.locals.isLoggedIn = false, then switches it to true only if there is a session with a user in it. That's the same req.session.user your login function stored.
4. res.locals.user = req.session.user || null makes the whole user object available to templates too, or null if nobody is logged in.
5. next() hands the request on to the next middleware or route.

This is why your header can use isLoggedIn on every page without each route passing it in. Because this middleware always sets it, the typeof check in your header is mostly a safety net. It only matters for a page rendered before this middleware runs, such as some error pages. It's harmless to keep.
